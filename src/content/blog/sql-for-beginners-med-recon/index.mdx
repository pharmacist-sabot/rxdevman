## 1. ฐานข้อมูลเชิงสัมพันธ์ (Relational Database) คืออะไร?

ก่อนจะเริ่มเขียน SQL เราต้องเข้าใจโครงสร้างข้อมูลกันก่อน ฐานข้อมูลเชิงสัมพันธ์จะจัดเก็บข้อมูลในรูปแบบของ **ตาราง (table)** ประกอบด้วย **คอลัมน์ (column)** ที่กำหนดชนิดของข้อมูล และ **แถว (row)** ที่แทนข้อมูลแต่ละรายการ โดยแต่ละแถวจะมี **คีย์หลัก (primary key)** ที่มีค่าไม่ซ้ำกันเพื่อใช้ระบุแถวนั้นๆ

ในระบบ HOSxP มีตารางที่ Med Recon นำมาใช้งานอยู่หลายตาราง ตัวอย่างตารางหลักๆ ได้แก่

| ตาราง | ข้อมูลที่จัดเก็บ | คอลัมน์สำคัญ |
|---|---|---|
| `patient` | ข้อมูลทั่วไปของผู้ป่วย | `hn`, `cid`, `fname`, `lname` |
| `opitemrece` | รายการสั่งจ่ายยา (ทั้ง OPD และ IPD) | `hn`, `vn`, `an`, `icode`, `qty` |
| `drugitems` | ข้อมูลรายการยาหลัก | `icode`, `name`, `strength`, `units` |
| `opd_allergy` | ประวัติการแพ้ยา | `hn`, `agent`, `symptom`, `report_date` |
| `ovst` | ประวัติการเข้ารับบริการผู้ป่วยนอก (OPD) | `vn`, `vstdate`, `main_dep` |
| `ipt` | ประวัติการนอนโรงพยาบาล (IPD) | `an`, `regdate`, `dchdate`, `ward` |

<InfoBox title="โจทย์การทำงานของ Med Recon" type="success">
  เมื่อผู้ใช้พิมพ์ชื่อผู้ป่วย เลข HN หรือเลขบัตรประชาชน แอปพลิเคชันจะต้องดึงข้อมูลส่วนตัว ประวัติการจ่ายยา ประวัติแพ้ยา และประวัติการรับบริการทั้งหมดขึ้นมาแสดงผลในหน้าจอเดียว ซึ่งเบื้องหลังการทำงานทั้งหมดนี้ เริ่มต้นจากคำสั่ง `SELECT` ทั้งสิ้น
</InfoBox>

## 2. คำสั่ง SELECT หัวใจสำคัญของการดึงข้อมูล

ในภาษา SQL มีคำสั่งพื้นฐานอยู่ 4 กลุ่ม คือ `SELECT` (อ่าน/ดึงข้อมูล), `INSERT` (เพิ่มข้อมูล), `UPDATE` (แก้ไขข้อมูล) และ `DELETE` (ลบข้อมูล) แต่สำหรับ Med Recon เราใช้เพียงแค่คำสั่ง `SELECT` เท่านั้น เนื่องจากมีกฎเหล็กว่า **ห้ามแก้ไขหรือเขียนข้อมูลทับลงในฐานข้อมูล HOSxP โดยเด็ดขาด**

ตัวอย่างคำสั่ง `SELECT` ที่เรียบง่ายที่สุดในโปรเจกต์ คือการค้นหาข้อมูลผู้ป่วย 1 คนด้วยเลข HN (`queries.rs:59`)

```sql
SELECT hn, cid, pname, fname, lname, birthday
FROM patient
WHERE hn = ?
LIMIT 1
```

เราสามารถแยกโครงสร้างคำสั่งได้ดังนี้

- `SELECT hn, cid, pname, fname, lname, birthday` ระบุคอลัมน์ที่ต้องการดึงข้อมูล โดยคั่นด้วยเครื่องหมายจุลภาค (,)
- `FROM patient` ระบุตารางที่ต้องการดึงข้อมูล
- `WHERE hn = ?` กรองเอาเฉพาะแถวที่มีเลข HN ตรงกับเงื่อนไขที่กำหนด
- `LIMIT 1` กำหนดให้ส่งผลลัพธ์กลับมาเพียงแถวเดียวเท่านั้น

สำหรับเครื่องหมาย `?` เรียกว่า **placeholder** ซึ่งจะอธิบายอย่างละเอียดในหัวข้อที่ 7 โดยให้เข้าใจเบื้องต้นว่ามันคือช่องว่างสำหรับใส่ค่าตัวแปรจริงตอนที่คำสั่งทำงาน

หลักการจำง่ายๆ คือ **SELECT คือจะเอาคอลัมน์ไหน, FROM คือเอาจากตารางอะไร, WHERE คือคัดกรองแถวไหน หรือมีเงื่อนไขอะไร** และ `LIMIT` คือกำหนดจำนวนผลลัพธ์สูงสุด

## 3. WHERE กับการกรองข้อมูลตามเงื่อนไข

คำสั่ง `WHERE` คือจุดที่ทำให้เราสามารถควบคุมข้อมูลได้ตามต้องการ โดยการสั่งให้ฐานข้อมูลส่งมาเฉพาะแถวที่ตรงกับเงื่อนไขเท่านั้น

### 3.1 การเปรียบเทียบค่าที่ตรงกันทุกประการ (=)

ตัวอย่างการค้นหาผู้ป่วยด้วยเลขประจำตัวประชาชน 13 หลัก (`queries.rs:16`)

```sql
SELECT hn, cid, pname, fname, lname, birthday
FROM patient
WHERE cid = ?
LIMIT ?
```

สังเกตว่า `LIMIT ?` ก็ใช้ placeholder เช่นกัน เนื่องจากตัวเลขจำกัดจำนวนผลลัพธ์ถูกส่งมาจากโค้ดของโปรแกรม (ในโปรเจกต์นี้ตั้งค่าเริ่มต้นไว้ที่ `DEFAULT_SEARCH_LIMIT = 20`)

### 3.2 LIKE สำหรับค้นหาข้อความบางส่วน

เวลาค้นหาด้วยชื่อ-นามสกุล ผู้ใช้อาจจำชื่อเต็มไม่ได้หรือพิมพ์แค่บางพยางค์ เราจึงต้องใช้ `LIKE` ร่วมกับ **wildcard** เพื่อค้นหาข้อความที่มีความคล้ายคลึง (`queries.rs:36`)

```sql
SELECT hn, cid, pname, fname, lname, birthday
FROM patient
WHERE fname LIKE ?
   OR lname LIKE ?
   OR CONCAT_WS(' ', pname, fname, lname) LIKE ?
LIMIT ?
```

จุดที่น่าสนใจในคำสั่งนี้มีดังนี้

1. **เครื่องหมาย `%` คือ wildcard** ที่ใช้แทน "ตัวอักษรอะไรก็ได้ กี่ตัวก็ได้" เช่น `สมชาย%` จะค้นพบ "สมชาย", "สมชาย ใจดี" ส่วน `%สมชาย%` จะครอบคลุมทั้ง "นายสมชาย" และ "สมชายใจดี" ซึ่งโค้ดของ Med Recon จะมีฟังก์ชันช่วยสร้าง pattern เหล่านี้ เช่น `prefix_pattern` (ค้นหาคำขึ้นต้น) และ `like_pattern` (ค้นหาคำที่ปรากฏอยู่ตรงไหนก็ได้)

2. **คำสั่ง `OR`** ใช้เชื่อมเงื่อนไขแบบ "อย่างใดอย่างหนึ่งเป็นจริง" นั่นคือ ชื่อจริงตรง หรือ นามสกุลตรง หรือ ชื่อ-นามสกุลเต็มตรง ก็ให้นำผลลัพธ์นั้นมาแสดง ต่างจาก `AND` ที่ต้องถูกต้องครบทุกเงื่อนไข

3. **`CONCAT_WS(' ', pname, fname, lname)`** เป็นฟังก์ชันที่ใช้รวมข้อความจากหลายคอลัมน์เข้าด้วยกันโดยมีตัวคั่น (WS ย่อมาจาก "With Separator") ในที่นี้คือการนำ คำนำหน้า + ชื่อ + นามสกุล มารวมกันโดยเว้นวรรค 1 ช่อง ทำให้สามารถค้นหาชื่อ-นามสกุลเต็ม เช่น "นายสมชาย ใจดี" ได้ทันที

<InfoBox title="ทำไมจึงควรค้นหาแบบขึ้นต้น (Prefix) ก่อน?" type="info">
  ในโค้ด Med Recon มีเทคนิคสำคัญคือ ระบบจะค้นหาชื่อแบบ **Prefix** (`สมชาย%`) ก่อนเสมอ เพราะฐานข้อมูลสามารถค้นหาผ่าน Index บนคอลัมน์ `fname`/`lname` ได้เร็วมาก หากไม่พบผลลัพธ์ จึงจะเปลี่ยนไปค้นหาแบบ Contains (`%สมชาย%`) ซึ่งทำงานช้ากว่าแต่ค้นหาได้ครอบคลุมกว่า
</InfoBox>

### 3.3 การรวมหลายเงื่อนไขด้วย AND, IS NULL และ TRIM

ลองมาดูคำสั่งที่ซับซ้อนขึ้นอย่างการดึงประวัติการจ่ายยาผู้ป่วยนอก (OPD) (`queries.rs:85`)

```sql
SELECT o.vn AS visit_id, o.hn, o.icode, CAST(o.qty AS CHAR) AS qty,
       o.vstdate AS disp_date,
       d.name AS drug_name, d.strength, d.units
FROM opitemrece o
JOIN drugitems d ON d.icode = o.icode
WHERE o.hn = ?
  AND o.vstdate >= ?
  AND (o.an IS NULL OR TRIM(o.an) = '')
ORDER BY o.vstdate
```

ในส่วนของ `WHERE` มี 3 เงื่อนไขหลักที่ต้องเป็นจริงพร้อมกัน (`AND`) ได้แก่

- `o.hn = ?` ระบุเลขประจำตัวผู้ป่วยที่ต้องการ
- `o.vstdate >= ?` กำหนดช่วงเวลาการจ่ายยา เช่น ดึงข้อมูลย้อนหลังไม่เกิน 2 ปีนับจากวันที่กำหนด
- `(o.an IS NULL OR TRIM(o.an) = '')` คัดเลือกเฉพาะรายการยาของ OPD เท่านั้น (รายการที่ไม่มีเลขการนอนโรงพยาบาล `an`)

เงื่อนไขสุดท้ายมีจุดสำคัญคือ **`IS NULL`** ใช้สำหรับตรวจสอบคอลัมน์ที่ "ไม่มีค่า" (ใน SQL ค่า `NULL` ไม่สามารถใช้เครื่องหมาย `=` ตรวจสอบได้) ส่วนฟังก์ชัน **`TRIM()`** ใช้สำหรับตัดช่องว่างหัวท้ายข้อความออก เพื่อป้องกันกรณีที่ข้อมูลในฐานข้อมูลไม่ใช่ `NULL` แต่เป็นข้อความว่างเปล่า เช่น `'   '`

### 3.4 การค้นหารายการยาด้วย LIKE ในหลายคอลัมน์

ตัวอย่างการค้นหายาจากตาราง `drugitems` (`queries.rs:199`)

```sql
SELECT icode, name, strength, units
FROM drugitems
WHERE icode LIKE ?
   OR name LIKE ?
ORDER BY name
LIMIT ?
```

ในกรณีนี้ เราใช้ `LIKE` แทนการใช้ `=` เพราะผู้ใช้งานมักจะพิมพ์เพียงบางส่วนของชื่อยา เช่น พิมพ์ "amox" เพื่อค้นหายา "Amoxicillin" การออกแบบคำสั่งค้นหาด้วย `LIKE` จึงตอบโจทย์การทำงานในช่องค้นหา (Search box) ได้ดีที่สุด

## 4. ORDER BY และ LIMIT เรียงลำดับและจำกัดผลลัพธ์

เมื่อต้องการดึงข้อมูลประวัติการรักษา เรามักต้องการเรียงลำดับตามวันเวลา ตัวอย่างการดึงประวัติการมารับบริการ OPD (`queries.rs:221`)

```sql
SELECT vn, vstdate, main_dep
FROM ovst
WHERE hn = ?
  AND vstdate >= ?
ORDER BY vstdate
```

คำสั่ง `ORDER BY vstdate` จะเรียงลำดับวันที่จากอดีตไปปัจจุบัน (น้อยไปมาก หรือเรียกว่า Ascending) แต่หากต้องการให้แสดงรายการล่าสุดขึ้นมาก่อน ให้ใส่คำว่า `DESC` (Descending) ต่อท้าย เช่น ตัวอย่างการดึงประวัติการตรวจร่างกาย (`queries.rs:158`)

```sql
SELECT vn, vstdate, cc, pe
FROM opdscreen
WHERE hn = ?
  AND vstdate >= ?
ORDER BY vstdate DESC
```

และหากต้องการเฉพาะข้อมูลประวัติการเจ็บป่วยในอดีต (PMH) ครั้งล่าสุดเพียงครั้งเดียว (`queries.rs:173`)

```sql
SELECT vstdate, pmh
FROM opdscreen
WHERE hn = ?
  AND pmh IS NOT NULL
  AND TRIM(pmh) <> ''
ORDER BY vstdate DESC
LIMIT 1
```

คำสั่งนี้ผสมผสานหลายเทคนิคเข้าด้วยกัน กรองเอาเฉพาะแถวที่มีการบันทึกประวัติจริง (`pmh IS NOT NULL` และ `TRIM(pmh) <> ''` โดยเครื่องหมาย `<>` หมายถึง "ไม่เท่ากับ") จากนั้นเรียงลำดับจากวันที่ล่าสุดลงมา (`ORDER BY vstdate DESC`) แล้วใช้ `LIMIT 1` เพื่อหยิบเฉพาะรายการล่าสุดเพียงรายการเดียว

<InfoBox title="ORDER BY + LIMIT = ดึงข้อมูลล่าสุด" type="success">
  รูปแบบ `ORDER BY [คอลัมน์วันที่] DESC LIMIT 1` เป็น Pattern ที่นิยมใช้บ่อยมากใน SQL เมื่อต้องการดึงข้อมูลครั้งล่าสุด หรือค่าที่มากที่สุดเพียงแถวเดียว เช่น การดึงประวัติอาการสำคัญ หรือวันนัดครั้งถัดไป
</InfoBox>

## 5. JOIN เชื่อมโยงข้อมูลข้ามตาราง

ในชีวิตจริง ข้อมูลไม่ได้ถูกเก็บรวมไว้ในตารางเดียวทั้งหมด เช่น ตารางจ่ายยา `opitemrece` จะเก็บเพียงรหัสยา `icode` เท่านั้น แต่ชื่อยาและรายละเอียดจะถูกเก็บไว้ในตาราง `drugitems` เราจึงต้องใช้คำสั่ง **JOIN** เพื่อเชื่อมตารางเหล่านี้เข้าด้วยกัน

### 5.1 INNER JOIN

ลองย้อนกลับมาดูคำสั่งจ่ายยา OPD ในหัวข้อ 3.3

```sql
FROM opitemrece o
JOIN drugitems d ON d.icode = o.icode
```

- `opitemrece o` เป็นการตั้งชื่อย่อ (alias) ให้กับตารางว่า `o` เพื่อให้เขียนโค้ดได้สั้นลง
- `JOIN drugitems d ON d.icode = o.icode` คือการเชื่อมกับตาราง `drugitems` (ชื่อย่อ `d`) โดยมีเงื่อนไขว่าค่า `icode` ของทั้งสองตารางต้องตรงกัน

การเขียน `JOIN` แบบนี้คือ **INNER JOIN** หมายถึง "จะดึงมาเฉพาะแถวที่มีข้อมูลตรงกันทั้งสองตารางเท่านั้น" หากรายการจ่ายยานั้นมีรหัสยาที่ไม่ปรากฏในตาราง `drugitems` แถวนั้นจะไม่ถูกนำมาแสดง

เมื่อเชื่อมตารางแล้ว เราจะสามารถเลือกคอลัมน์จากทั้งสองตารางมาแสดงพร้อมกันได้ทันที

```sql
SELECT o.vn AS visit_id, o.icode, d.name AS drug_name, d.strength, d.units
```

คำสั่ง **`AS`** ใช้สำหรับเปลี่ยนชื่อคอลัมน์ในผลลัพธ์ (Column Alias) เช่น `o.vn AS visit_id` ช่วยให้โค้ดฝั่งแอปพลิเคชันนำผลลัพธ์ไปประมวลผลต่อได้เข้าใจง่ายขึ้น

### 5.2 LEFT JOIN ดึงข้อมูลฝั่งซ้ายมาครบทุกแถว

ต่างจาก INNER JOIN ที่ต้องมีข้อมูลตรงกันทั้งสองฝั่ง **LEFT JOIN** จะดึงข้อมูลจากตารางหลัก (ตารางฝั่งซ้าย) มาทั้งหมดเสมอ แม้ว่าจะไม่พบข้อมูลที่ตรงกันในตารางฝั่งขวาก็ตาม (ข้อมูลฝั่งขวาจะแสดงเป็น `NULL`)

ดูตัวอย่างการดึงข้อมูลวิธีใช้ยา (sig) (`queries.rs:144`)

```sql
SELECT o.vn, o.an, o.icode,
       d.name1 AS d_name1, d.name2 AS d_name2, d.name3 AS d_name3,
       s.name1 AS s_name1, s.name2 AS s_name2, s.name3 AS s_name3
FROM opitemrece o
LEFT JOIN drugusage d ON d.drugusage = o.drugusage
LEFT JOIN sp_use s ON s.sp_use = o.sp_use
WHERE o.hn = ?
  AND o.vstdate >= ?
```

รายการจ่ายยาบางรายการอาจไม่มีการระบุรหัสวิธีใช้ยามาตรฐาน (`drugusage`) หรือวิธีใช้ยาพิเศษ (`sp_use`) หากเราใช้ `INNER JOIN` รายการยาเหล่านั้นจะหลุดหายไปจากรายงานทันที แต่การใช้ `LEFT JOIN` จะทำให้รายการยายังคงอยู่ครบถ้วน เพียงแต่วิธีใช้ยาจะแสดงเป็น `NULL` ซึ่งโปรแกรมสามารถนำไปจัดการต่อได้

  </FeatureCard>
  <FeatureCard title="LEFT JOIN" icon="arrow-right-circle">
    ดึงข้อมูลฝั่งซ้ายมาทั้งหมดเสมอ แม้ฝั่งขวาจะไม่มีข้อมูล เหมาะสำหรับข้อมูลเสริม เช่น วิธีการใช้ยา หรือคำแนะนำพิเศษ
  </FeatureCard>
</FeatureGrid>

## 6. ฟังก์ชันและการจัดกลุ่มข้อมูลด้วย GROUP BY

### 6.1 CAST แปลงชนิดข้อมูล

ในคำสั่งดึงรายการยา OPD มีการใช้ `CAST(o.qty AS CHAR) AS qty` ทำไมถึงต้องแปลงชนิดข้อมูล?

เหตุผลคือในฐานข้อมูล HOSxP คอลัมน์ `qty` (จำนวนยา) ถูกเก็บเป็นประเภท `DECIMAL` ซึ่งไลบรารี sqlx (ตัวเชื่อมต่อฐานข้อมูล MySQL ในภาษา Rust) อาจมีปัญหากับชนิดข้อมูลนี้เมื่อต้องแปลงค่าลงตัวแปร โค้ดจึงสั่งให้ SQL แปลงตัวเลขเป็นข้อความ (`CHAR`) เสียก่อน แล้วจึงค่อยให้โปรแกรมแปลงเป็นตัวเลขอีกครั้ง นี่เป็นตัวอย่างที่ดีของการแก้ปัญหาหน้างานจริงในระดับระบบ

### 6.2 MAX ร่วมกับ GROUP BY หาค่าสูงสุดของแต่ละกลุ่ม

ตัวอย่างการดึงวันนัดหมายครั้งถัดไปของผู้ป่วย (`queries.rs:245`)

```sql
SELECT vn, MAX(nextdate) AS nextdate
FROM oapp
WHERE hn = ?
  AND vstdate >= ?
  AND nextdate IS NOT NULL
GROUP BY vn
```

ในการมารับบริการหนึ่งครั้ง (`vn`) ผู้ป่วยอาจมีรายการนัดหมายหลายคลินิก (เช่น นัดตรวจเลือด, นัดพบแพทย์) เราต้องการทราบ "วันนัดที่ไกลที่สุดหรือล่าสุด" จึงใช้ฟังก์ชัน `MAX(nextdate)` และใช้ **`GROUP BY vn`** เพื่อสั่งให้ระบบจัดกลุ่มข้อมูลตามครั้งที่มารับบริการ

หลักการจำคือ **GROUP BY ใช้รวมแถวที่มีค่าเหมือนกันเข้าด้วยกันเป็นกลุ่ม แล้วคำนวณผลสรุปของแต่ละกลุ่มด้วย Aggregate Functions เช่น MAX, MIN, COUNT หรือ SUM** โดยคอลัมน์ใน SELECT ที่ไม่ได้อยู่ในฟังก์ชันสรุป จะต้องถูกนำมาใส่ไว้หลัง GROUP BY เสมอ

## 7. Parameterized Query ความปลอดภัยที่มองข้ามไม่ได้

สังเกตว่าทุกคำสั่ง SQL ที่ผ่านมา มีการใช้เครื่องหมาย `?` แทนการนำตัวแปรจริงไปวางตรงๆ ในคำสั่งเสมอ ซึ่งนี่คือหัวใจสำคัญด้านความปลอดภัยของระบบฐานข้อมูล

ลองนึกภาพว่าหากเราเขียน SQL ด้วยการนำข้อความมาต่อกันโดยตรง (String Concatenation)

```sql
-- ❌ ตัวอย่างที่ไม่ปลอดภัยและห้ามทำเด็ดขาด (เสี่ยงต่อ SQL Injection)
SELECT * FROM patient WHERE fname = 'สมชาย'
```

หากมีผู้ใช้งานกรอกข้อความในช่องค้นหาว่า `สมชาย' OR '1'='1` คำสั่ง SQL ที่เกิดขึ้นจริงจะกลายเป็น

```sql
SELECT * FROM patient WHERE fname = 'สมชาย' OR '1'='1'
```

เงื่อนไข `'1'='1'` จะเป็นจริงเสมอ ทำให้ระบบส่งข้อมูลผู้ป่วยทั้งหมดในโรงพยาบาลออกมา หรือหากมีผู้ไม่หวังดีส่งคำสั่งอันตรายอย่าง `'; DROP TABLE patient; --` เข้ามา ฐานข้อมูลอาจถูกลบหายไปทั้งตาราง ช่องโหว่นี้เรียกว่า **SQL Injection**

ทางออกที่ถูกต้องคือการใช้ **Parameterized Query (Prepared Statement)** โดยเขียนคำสั่งด้วยเครื่องหมาย `?` แล้วส่งค่าตัวแปรแยกออกไปต่างหาก ตัวฐานข้อมูลจะมองว่าค่าที่ส่งไปเป็น "ข้อมูลธรรมดา" เสมอ ไม่ใช่ "คำสั่งที่นำไปประมวลผล"

ดูตัวอย่างการเรียกใช้จริงในภาษา Rust จากไฟล์ `client.rs:591`

```rust
async fn fetch_rows<T>(&self, stmt: &str, params: &[P]) -> Result<Vec<T>>
where
    T: for<'r> sqlx::FromRow<'r, sqlx::mysql::MySqlRow> + Send + Unpin,
{
    assert_read_only(stmt)?;
    let mut query = sqlx::query_as::<_, T>(stmt);
    for p in params {
        query = match p {
            P::Str(v) => query.bind(v),
            P::Date(v) => query.bind(*v),
            P::Int(v) => query.bind(*v),
        };
    }
    Ok(query.fetch_all(&self.pool).await?)
}
```

ในโปรเจกต์จริงจะมีการระบุประเภทข้อมูลของตัวแปรอย่างชัดเจน (`P::Str`, `P::Date`, `P::Int`) เพื่อให้ MySQL ทำงานกับคำสั่งอย่าง `LIMIT` หรือการเปรียบเทียบวันที่ได้อย่างถูกต้องแม่นยำ

### 7.1 การจัดการกับ Wildcard ในคำสั่ง LIKE

แม้ว่าจะใช้ Parameterized Query แล้ว หากผู้ใช้พิมพ์เครื่องหมาย `%` หรือ `_` เข้ามาในช่องค้นหา ฐานข้อมูลจะมองว่าตัวอักษรเหล่านั้นเป็น Wildcard ของคำสั่ง LIKE ซึ่งอาจทำให้ผลลัพธ์เพี้ยนไปจากที่ต้องการ โปรเจกต์ Med Recon จึงเขียนฟังก์ชัน Escape ข้อความเตรียมไว้ (`queries.rs:254`)

```rust
pub fn escape_like(s: &str) -> String {
    let mut out = String::with_capacity(s.len());
    for ch in s.chars() {
        match ch {
            '%' | '_' | '\\' => {
                out.push('\\');
                out.push(ch);
            }
            _ => out.push(ch),
        }
    }
    out
}
```

ฟังก์ชันนี้จะใส่เครื่องหมาย Backslash (`\`) นำหน้าตัวอักษรพิเศษ `%`, `_` และ `\` โดยอัตโนมัติ เช่น หากผู้ใช้ค้นหาคำว่า `50%` ข้อความจะถูกแปลงเป็น `50\%` เพื่อให้ฐานข้อมูลค้นหาคำว่า "50%" จริงๆ

<InfoBox title="สรุปกลไกป้องกัน 3 ระดับ" type="danger">
  1. **Parameterized Query** ป้องกันไม่ให้ข้อความจากผู้ใช้กลายเป็นคำสั่ง SQL (แก้ SQL Injection)
  2. **Escape LIKE Wildcard** ป้องกันไม่ให้อักขระพิเศษอย่าง `%` และ `_` ถูกตีความผิดในคำสั่ง LIKE
  3. **Read-Only Guard** ป้องกันในระดับแอปพลิเคชัน ไม่ให้มีการรันคำสั่งแก้ไขข้อมูลอย่างเด็ดขาด (ดูต่อในหัวข้อที่ 8)
</InfoBox>

## 8. Read-Only Guard ด่านตรวจความปลอดภัยระดับแอปพลิเคชัน

ส่วนที่น่าสนใจมากของโปรเจกต์นี้ คือไฟล์ `readonly.rs` ซึ่งทำหน้าที่เป็นด่านตรวจคอยตรวจสอบคำสั่ง SQL ทุกคำสั่งก่อนที่จะถูกส่งไปทำงานยังฐานข้อมูล HOSxP

```rust
const ALLOWED_KEYWORDS: [&str; 4] = ["select", "show", "describe", "explain"];

pub fn assert_read_only(stmt: &str) -> Result<()> {
    let first = stmt
        .split_whitespace()
        .next()
        .map(str::to_lowercase)
        .unwrap_or_default();
    if ALLOWED_KEYWORDS.contains(&first.as_str()) {
        Ok(())
    } else {
        Err(Error::ReadOnlyViolation(
            stmt.trim().chars().take(64).collect(),
        ))
    }
}
```

การทำงานคือ โปรแกรมจะตรวจสอบคำแรกของคำสั่ง SQL และอนุญาตให้ทำงานได้เฉพาะคำสั่ง `SELECT`, `SHOW`, `DESCRIBE` และ `EXPLAIN` เท่านั้น หากพบคำสั่งประเภท `INSERT`, `UPDATE`, `DELETE`, `DROP` หรือแม้กระทั่ง `WITH` (ที่อาจมี `WITH ... DELETE` ซ่อนอยู่) ระบบจะปฏิเสธการทำงานทันที

และในชุดทดสอบ Unit Test (`readonly.rs:50`) ก็มีการทดสอบคำสั่งอันตรายไว้อย่างชัดเจน

```rust
for stmt in [
    "INSERT INTO patient (hn) VALUES ('x')",
    "UPDATE patient SET fname = 'x'",
    "DELETE FROM patient",
    "DROP TABLE patient",
    "ALTER TABLE patient ADD COLUMN x INT",
    "CREATE TABLE evil (x INT)",
    "WITH cte AS (SELECT 1) DELETE FROM patient",
    "TRUNCATE TABLE patient",
] {
    assert!(assert_read_only(stmt).is_err(), "must reject: {stmt}");
}
```

นี่คือแนวคิด **Defense in Depth** (การป้องกันแบบหลายชั้น) ที่แม้ว่าเราจะตั้งค่าสิทธิ์ของผู้ใช้ในฐานข้อมูล (Database User) เป็นแบบอ่านอย่างเดียวแล้ว แต่ในระดับโค้ดของแอปพลิเคชันก็ยังมีตัวกรองอีกชั้นหนึ่ง เพื่อป้องกันข้อผิดพลาดที่อาจเกิดขึ้นโดยไม่ตั้งใจ

## 9. บทสรุป

จากตัวอย่างการใช้งานจริงในบทความนี้ เราได้เรียนรู้คำสั่งสำคัญของ SQL ครบถ้วน

| หัวข้อ | คำสั่ง / คีย์เวิร์ด | ตัวอย่างการใช้งานใน Med Recon |
|---|---|---|
| อ่านข้อมูล | `SELECT ... FROM ...` | `SELECT hn, cid, pname FROM patient` |
| กรองข้อมูล | `WHERE`, `AND`, `OR`, `LIKE`, `IS NULL`, `TRIM()` | ค้นหาผู้ป่วยด้วย HN, CID หรือชื่อ-นามสกุล |
| เรียงลำดับและจำกัดจำนวน | `ORDER BY`, `LIMIT` | ดึงประวัติการรักษาล่าสุด, จำกัดผลค้นหา 20 รายการ |
| เชื่อมโยงตาราง | `JOIN ... ON`, `LEFT JOIN` | เชื่อมตารางจ่ายยา `opitemrece` กับชื่อยา `drugitems` |
| จัดกลุ่มและสรุปผล | `GROUP BY`, `MAX()` | สรุปหาวันนัดหมายล่าสุดของแต่ละครั้งบริการ |
| ปรับแต่งและแปลงข้อมูล | `CAST()`, `CONCAT_WS()`, Alias (`AS`) | แปลงชนิดข้อมูลจำนวนยา, รวมชื่อ-นามสกุล |
| ความปลอดภัย | `?` (Placeholder), Escape, Read-Only Guard | ป้องกัน SQL Injection และคำสั่งแก้ไขข้อมูลทุกรูปแบบ |

สิ่งที่สำคัญไม่แพ้เรื่องของ Syntax คือ **วิธีคิดในการเขียน SQL บนระบบงานจริง** 3 ข้อ ได้แก่

1. **ใช้ Parameterized Query เสมอ** อย่าใช้วิธีต่อข้อความ (String Concatenation) เด็ดขาด
2. **คำนึงถึงข้อมูลจริง** ค่าว่างในระบบจริงอาจเป็นได้ทั้ง `NULL` หรือข้อความว่างเปล่า (`''`) และตัวอักษรพิเศษของผู้ใช้อาจส่งผลต่อการทำงานของคำสั่งค้นหา
3. **เลือกประเภท JOIN ให้ตรงจุดประสงค์** ใช้ `INNER JOIN` เมื่อข้อมูลจำเป็นต้องมีทั้งสองฝั่ง และใช้ `LEFT JOIN` เมื่อต้องการเก็บข้อมูลฝั่งหลักไว้แม้ไม่มีข้อมูลเสริม

หากต้องการศึกษาเพิ่มเติม ขอแนะนำให้ลองเปิดดูโค้ดจริงในโปรเจกต์ [med-recon](https://github.com/suradet-ps/med-recon) ที่ไฟล์ `crates/med-recon-hosxp/src/queries.rs` เพื่อดูโครงสร้างคำสั่งและการเขียนเทสต์ควบคู่กัน การได้อ่านโค้ดและทดลองใช้งานจริงกับฐานข้อมูล คือก้าวสำคัญที่จะช่วยให้คุณเข้าใจภาษา SQL ได้อย่างลึกซึ้งครับ
