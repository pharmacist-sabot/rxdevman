Git คือหัวใจของการพัฒนาซอฟต์แวร์ในปัจจุบัน ไม่ว่าคุณจะเป็นนักพัฒนา Frontend, Backend, Data Scientist หรือ DevOps การเข้าใจ Git คือทักษะพื้นฐานที่ขาดไม่ได้

บทความนี้คือคู่มือที่จะพาคุณเจาะลึก 12 คำสั่ง Git ที่สำคัญที่สุด ซึ่งเป็นเครื่องมือที่คุณจะได้ใช้ทุกวัน โดยอ้างอิงและขยายความจาก Cheat Sheet ที่ยอดเยี่ยมของ [Sysxplore](https://sysxplore.com/)

<InfoBox title="หัวใจของ Git: 3 พื้นที่หลัก" type="info">
  ก่อนจะเริ่ม เราต้องเข้าใจก่อนว่า Git ทำงานกับ 3 พื้นที่หลัก:
  <ol>
    <li>
      <strong>Working Directory:</strong> โฟลเดอร์โปรเจกต์ของคุณ
      ที่คุณสร้างและแก้ไขไฟล์ต่างๆ
    </li>
    <li>
      <strong>Staging Area (Index):</strong> พื้นที่พักไฟล์ "ฉบับร่าง"
      ที่คุณเตรียมจะบันทึก (Commit)
    </li>
    <li>
      <strong>Local Repository (.git):</strong> "เซฟเกม"
      ของคุณที่เก็บประวัติการเปลี่ยนแปลงทั้งหมดไว้ในเครื่อง
    </li>
  </ol>
  คำสั่งส่วนใหญ่คือการย้ายไฟล์ระหว่าง 3 พื้นที่นี้ และซิงค์กับ Remote Repository
  (เช่น GitHub)
</InfoBox>

## Workflow พื้นฐาน (The Daily Grind)

มาเริ่มกันที่กลุ่มคำสั่งที่คุณจะได้ใช้บ่อยที่สุดในแต่ละวัน

<GitCommand command="git init" icon="archive-box-arrow-down">
  <p><strong>หน้าที่:</strong> สร้าง Repository ใหม่ในโปรเจกต์ของคุณ</p>
  <p>
    นี่คือคำสั่งแรกสุดที่คุณจะใช้กับโปรเจกต์ที่ยังไม่เคยใช้ Git มาก่อน มันจะสร้างโฟลเดอร์ซ่อนที่ชื่อว่า <code>.git</code> ขึ้นมา ซึ่งเป็นที่เก็บข้อมูลประวัติทั้งหมดของโปรเจกต์คุณ
  </p>

```bash
$ mkdir my-new-project
$ cd my-new-project
$ git init
Initialized empty Git repository in /path/to/my-new-project/.git/
```

  <p>
      💡 ถ้ามี repository อยู่บน GitHub อยู่แล้ว ให้ใช้คำสั่ง <code>git clone</code> แทน
    </p>
</GitCommand>

<GitCommand command="git status" icon="magnifying-glass">
  <p><strong>หน้าที่:</strong> ตรวจสอบสถานะปัจจุบันของ Repository</p>
  <p>
    คำสั่งนี้เปรียบเสมือน "GPS" ของคุณใน Git มันจะบอกคุณว่ามีไฟล์ไหนที่ถูกแก้ไข (Modified), ไฟล์ไหนที่ถูกเพิ่มเข้า Staging Area แล้ว (Staged), หรือไฟล์ไหนที่ Git ยังไม่รู้จัก (Untracked) <strong>ใช้คำสั่งนี้บ่อยๆ</strong>
  </p>

```bash
$ git status
On branch main
No commits yet
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        hello.txt

nothing added to commit but untracked files present (use "git add" to track)
```

</GitCommand>

<GitCommand command="git add" icon="plus-circle">
  <p><strong>หน้าที่:</strong> เพิ่มการเปลี่ยนแปลงไปยัง Staging Area</p>
  <p>
    หลังจากที่คุณแก้ไขไฟล์เสร็จแล้ว คำสั่งนี้จะเปรียบเสมือนการ "หยิบของใส่ตะกร้า" เพื่อเตรียมตัวไปจ่ายเงิน (Commit) เป็นการบอก Git ว่าการเปลี่ยนแปลงในไฟล์นี้พร้อมที่จะถูกบันทึกแล้ว
  </p>
  <CodeExplainer title="รูปแบบการใช้งาน git add">
    <details>
      <summary><code>git add &lt;file-name&gt;</code></summary>
      <p>เพิ่มไฟล์ที่ระบุเพียงไฟล์เดียวเข้าสู่ Staging Area</p>
    </details>
    <details>
      <summary><code>git add .</code></summary>
      <p>เพิ่มไฟล์ที่ถูกแก้ไขหรือสร้างขึ้นใหม่ทั้งหมดใน Directory ปัจจุบันและ Subdirectory เข้าสู่ Staging Area (ใช้บ่อยที่สุด)</p>
    </details>
  </CodeExplainer>

```bash
$ echo "# My Project" >> README.md
$ git add README.md
```

</GitCommand>

<GitCommand command="git commit" icon="bookmark">
  <p><strong>หน้าที่:</strong> บันทึกการเปลี่ยนแปลงจาก Staging Area ไปยัง Local Repository</p>
  <p>
    นี่คือการ "สร้างจุดเซฟ" อย่างเป็นทางการ ทุก Commit คือสแนปช็อตของโปรเจกต์ ณ เวลานั้นๆ พร้อมกับข้อความ (Commit Message) ที่อธิบายว่าคุณทำอะไรไปบ้าง
    <a href="/blog/git-commit-messages/">การเขียน Commit Message ที่ดี</a> คือทักษะที่สำคัญมาก
  </p>

```bash
# วิธีที่ 1: ใส่ message ในคำสั่งโดยตรง (สำหรับข้อความสั้นๆ)
$ git commit -m "feat: Add initial README file"

# วิธีที่ 2: เปิด Text Editor เพื่อเขียน message (สำหรับข้อความยาวๆ)
$ git commit
```

  <InfoBox title="Pro Tip: เขียน Commit Message อย่างไรให้ดี?" type="success">
    การเขียน Commit Message ที่ชัดเจนและเป็นมาตรฐานคือหัวใจของการทำงานร่วมกัน อ่านคู่มือฉบับสมบูรณ์ที่ผมเคยเขียนไว้เพื่อเรียนรู้เทคนิคระดับมืออาชีพได้ที่: <a href="/blog/git-commit-messages/">คู่มือการเขียน Git Commit Message</a>
  </InfoBox>
</GitCommand>

## การทำงานกับ Branches (Branching)

Branches คือหัวใจที่ทำให้ Git ทรงพลัง มันช่วยให้คุณสามารถสร้าง "เส้นทาง" แยกออกมาเพื่อพัฒนาฟีเจอร์ใหม่หรือทดลองอะไรบางอย่าง โดยไม่กระทบกับโค้ดหลัก (main)

<GitCommand command="git branch" icon="arrows-right-left">
  <p><strong>หน้าที่:</strong> จัดการ Branches</p>
  <p>
    ใช้สำหรับดูรายการ Branch ทั้งหมด, สร้าง Branch ใหม่, หรือลบ Branch ที่ไม่ต้องการแล้ว
  </p>

```bash
# ดู Branch ทั้งหมด (Branch ปัจจุบันจะมี * นำหน้า)
$ git branch

# สร้าง Branch ใหม่ชื่อ 'feature-login'
$ git branch feature-login

# ลบ Branch (ต้องอยู่ Branch อื่นก่อน)
$ git branch -d feature-login
```

</GitCommand>

<GitCommand command="git checkout" icon="arrow-uturn-right">
  <p><strong>หน้าที่:</strong> สลับไปยัง Branch ที่ต้องการ</p>
  <p>
    คำสั่งนี้ใช้เพื่อ "ย้าย" ไปทำงานใน Branch อื่น เมื่อคุณ checkout ไปยัง Branch ใหม่ ไฟล์ใน Working Directory ของคุณจะถูกเปลี่ยนเป็นเวอร์ชันล่าสุดของ Branch นั้นๆ
  </p>

```bash
# สลับไปทำงานที่ Branch 'feature-login'
$ git checkout feature-login

# สร้างและสลับไปยัง Branch ใหม่ในคำสั่งเดียว
$ git checkout -b new-feature
```

<InfoBox title="คำแนะนำ: ใช้ git switch ดีกว่า" type="success">
    ใน Git เวอร์ชันใหม่ๆ แนะนำให้ใช้ <code>git switch &lt;branch-name&gt;</code> เพื่อสลับ Branch และ <code>git restore &lt;file-name&gt;</code> เพื่อยกเลิกการแก้ไขไฟล์ ซึ่งสื่อความหมายได้ชัดเจนกว่า <code>git checkout</code> ที่ทำได้หลายหน้าที่
  </InfoBox>
</GitCommand>

<GitCommand command="git merge" icon="arrows-pointing-in">
  <p><strong>หน้าที่:</strong> รวมการเปลี่ยนแปลงจาก Branch หนึ่งเข้ามายัง Branch ปัจจุบัน</p>
  <p>
    เมื่อคุณพัฒนาฟีเจอร์ใน Branch ของคุณเสร็จแล้ว Workflow ปกติคือการสลับกลับมาที่ Branch หลัก (เช่น `main`) แล้วใช้คำสั่งนี้เพื่อดึงโค้ดใหม่ทั้งหมดเข้ามารวมกัน
  </p>

```bash
# 1. กลับไปที่ Branch หลัก
$ git checkout main

# 2. รวม Branch 'feature-login' เข้ามา
$ git merge feature-login
```

</GitCommand>

## การทำงานกับ Remote Repository

เมื่อคุณทำงานเป็นทีม หรือต้องการสำรองโค้ดของคุณไว้บน Cloud (เช่น GitHub, GitLab) คุณจะต้องใช้คำสั่งกลุ่มนี้

<GitCommand command="git remote" icon="cloud-arrow-up">
  <p><strong>หน้าที่:</strong> จัดการการเชื่อมต่อกับ Remote Repository</p>
  <p>
    ใช้สำหรับเพิ่ม, ดู, หรือลบการเชื่อมต่อกับ Repository ปลายทาง โดยทั่วไปเรามักจะตั้งชื่อ Remote หลักว่า `origin`
  </p>

```bash
# เพิ่ม Remote ใหม่ชื่อ 'origin'
$ git remote add origin <repository-url>

# ดูรายการ Remote ทั้งหมดพร้อม URL
$ git remote -v

# เปลี่ยนชื่อ Remote
$ git remote rename origin upstream
```

</GitCommand>

<GitCommand command="git push" icon="arrow-up-on-square">
  <p><strong>หน้าที่:</strong> ส่ง (Push) Local Commits ไปยัง Remote Repository</p>
  <p>
    หลังจากที่คุณ Commit การเปลี่ยนแปลงในเครื่องของคุณแล้ว คำสั่งนี้จะทำการ "อัปโหลด" ประวัติการเปลี่ยนแปลงนั้นขึ้นไปเก็บไว้ที่ Remote เพื่อแชร์ให้คนอื่นในทีมเห็น
  </p>

```bash
# Push Branch 'main' ปัจจุบันไปยัง Remote 'origin'
$ git push origin main
```

  <InfoBox title="Pro Tip: ความแตกต่างระหว่าง `git push` และ `git push -u`" type="success">
    <p>
      เมื่อทำการ push branch ใหม่เป็นครั้งแรก แนะนำให้ใช้ flag <code>-u</code> (หรือ <code>--set-upstream</code>) เสมอครับ
    </p>

    <p><strong>🔶 <code>git push origin main</code></strong></p>
    <ul>
      <li><strong>หน้าที่:</strong> ส่ง branch <code>main</code> ขึ้นไปยัง remote <code>origin</code></li>
      <li><strong>ข้อสังเกต:</strong> Git จะยังไม่จำว่า branch ทั้งสองนี้เชื่อมต่อกัน ครั้งต่อไปคุณจึงต้องพิมพ์คำสั่งเต็มๆ อีกครั้ง</li>
    </ul>

    <p><strong>🔶 <code>git push -u origin main</code></strong></p>
    <ul>
      <li><strong>หน้าที่:</strong> ส่ง branch <code>main</code> ไปยัง <code>origin</code> <strong>และตั้งค่าให้เป็น upstream branch (คู่ติดตาม)</strong></li>
      <li><strong>ประโยชน์:</strong> ตั้งแต่ครั้งถัดไป คุณสามารถใช้คำสั่งสั้นๆ ได้เลย เช่น <code>git push</code> หรือ <code>git pull</code> โดยไม่ต้องระบุ remote และ branch อีก</li>
    </ul>

  </InfoBox>
</GitCommand>

<GitCommand command="git fetch" icon="arrow-down-tray">
  <p><strong>หน้าที่:</strong> ดึงข้อมูลล่าสุดจาก Remote แต่ยังไม่รวมเข้ากับโค้ดของคุณ</p>
  <p>
    คำสั่งนี้จะทำการ "ดาวน์โหลด" ประวัติการเปลี่ยนแปลงทั้งหมดจาก Remote มาเก็บไว้ในเครื่องของคุณ แต่จะยังไม่แตะต้องโค้ดใน Working Directory ของคุณเลย นี่เป็นวิธีที่ปลอดภัยในการ "แอบดู" ว่ามีอะไรอัปเดตบ้าง
  </p>

```bash
$ git fetch origin
```

</GitCommand>

<GitCommand command="git pull" icon="arrows-up-down">
  <p><strong>หน้าที่:</strong> ดึงข้อมูลล่าสุดจาก Remote และรวมเข้ากับ Branch ปัจจุบันทันที</p>
  <p>
    คำสั่งนี้เป็นเหมือนการทำ 2 อย่างในขั้นตอนเดียว คือ <code>git fetch</code> แล้วตามด้วย <code>git merge</code> ทันที เหมาะสำหรับ Workflow ที่ต้องการอัปเดตโค้ดให้เป็นเวอร์ชันล่าสุดอย่างรวดเร็ว
  </p>

```bash
$ git pull origin main
```

  <InfoBox title="Fetch vs. Pull: อะไรดีกว่ากัน?">
    <ul>
      <li><strong>git fetch:</strong> ปลอดภัยกว่า เพราะให้โอกาสคุณได้ตรวจสอบการเปลี่ยนแปลงก่อน (ด้วย <code>git log origin/main</code>) แล้วค่อยตัดสินใจ <code>merge</code> เอง</li>
      <li><strong>git pull:</strong> สะดวกและเร็วกว่า แต่ถ้ามี Conflict (โค้ดขัดแย้งกัน) มันจะเกิดขึ้นทันทีใน Working Directory ของคุณ</li>
    </ul>
    <strong>สำหรับมือใหม่:</strong> การใช้ <code>git pull</code> ก็เพียงพอและเข้าใจง่าย แต่เมื่อทำงานในทีมที่ซับซ้อน การหันมาใช้ <code>fetch</code> + <code>merge</code> จะช่วยให้ควบคุมได้ดีกว่า
  </InfoBox>
</GitCommand>

## คำสั่งสำหรับแก้ไขอดีต (Advanced)

<GitCommand command="git reset" icon="arrow-uturn-left">
  <p><strong>หน้าที่:</strong> ย้อนสถานะของ Branch กลับไปยัง Commit ที่ต้องการ</p>
  <p>
    นี่คือ "ไทม์แมชชีน" ของ Git แต่ก็เป็นคำสั่งที่ต้องใช้อย่างระมัดระวัง เพราะมันสามารถลบประวัติการทำงานของคุณได้
  </p>
  <CodeExplainer title="3 โหมดหลักของ git reset">
    <details>
      <summary><code>--soft</code></summary>
      <p>ย้อนกลับแค่ "หัวชี้" (HEAD) ของ Branch แต่การเปลี่ยนแปลงทั้งหมดจะยังคงอยู่ใน Staging Area เหมาะสำหรับรวมหลายๆ Commit เป็นอันเดียว</p>
    </details>
    <details>
      <summary><code>--mixed</code> (ค่าเริ่มต้น)</summary>
      <p>ย้อนกลับทั้ง HEAD และ Staging Area แต่ไฟล์ที่แก้ไขจะยังคงอยู่ใน Working Directory ของคุณ เหมาะสำหรับยกเลิก Commit ล่าสุดแต่ยังเก็บโค้ดไว้</p>
    </details>
    <details>
      <summary><code>--hard</code></summary>
      <p><strong>(อันตราย!)</strong> ย้อนกลับทุกอย่าง ทั้ง HEAD, Staging Area, และ Working Directory การเปลี่ยนแปลงทั้งหมดที่ทำหลัง Commit นั้นจะหายไปอย่างถาวร</p>
    </details>
  </CodeExplainer>

```bash
# ดูประวัติ Commit เพื่อหา hash ที่ต้องการ
$ git log --oneline

# ย้อนกลับไป 1 commit แต่เก็บการเปลี่ยนแปลงไว้ใน Working Directory
$ git reset HEAD~1

# ย้อนกลับไปที่ commit ที่ระบุและทิ้งทุกอย่าง (ใช้ด้วยความระมัดระวัง!)
$ git reset --hard <commit-hash>
```

</GitCommand>

## สรุป
